# 플랫폼 데이터 조사

> **확인일: 2026. 10. 19.** 민관협력 지원 플랫폼 이용 상태가 승인 전으로 표시되므로 이 조사에서 플랫폼 카탈로그 항목을 호출하거나 활용 신청하지 않았다. 상세 화면의 신청 버튼이 보였으며, 실제 승인 절차와 승인 여부는 확인되지 않았다. 아래 데이터는 플랫폼이 연결한 원본 제공처에서 신청 및 승인 절차를 별도로 확인해야 한다.

## 조사 범위와 한계

- `https://digitalsolveup.kr/data`에서 목록 609건, 61쪽을 확인했다. 플랫폼 내부 목록 조회 주소에서 100건씩 나눠 확인했고, 상세 609건을 점검했다.
- 사이트의 형식 태그는 JSON 458건, XML 488건, CSV 3건으로 합계가 항목 수와 일치하지 않는다. 복수 형식 태그로 보이나 정확한 중복 기준은 사이트에서 설명하지 않는다.
- 상세 화면에는 요청 및 응답 필드 표가 없었다. `accrualPeriodicity` 값도 유효한 갱신 주기로 확인할 수 없었다. 목록의 갱신일은 최종 수정일이며 갱신 주기가 아니다.
- 따라서 필드, 갱신 주기, 실제 사용 승인 필요 여부가 원문에 없으면 추정하지 않고 `원본 확인 필요`로 기록했다.

## 필요한 신청과 검증 순서

1. 플랫폼의 사용 신청 승인 상태와 이용기간을 확인한다. 승인 전에는 키 발급과 호출을 시도하지 않는다.
2. 우선 후보를 산불위험지수, 기상특보, 단기예보, 장기요양기관, GIS 건물 자료로 좁힌다. 이들 중 상당수는 프로젝트에서 공공데이터포털 원본을 이미 사용하므로 중복과 이용 조건을 비교한다.
3. 각 항목의 상세에서 원본 제공처 링크를 열어 서비스키 발급 조건, 응답 필드, 이용약관, 호출 제한, 갱신 주기를 확인한다.
4. 승인 뒤 비밀값은 서버 환경변수로만 보관한다. 화면은 `대기`, `연결됨`, `호출 실패` 상태를 분리하고 원문 출처와 자료 시각을 같이 표시한다.
5. 실제 응답을 확보한 뒤 개발 및 시험 데이터와 분리해 기록한다. 데이터 수치와 매핑 규칙은 확인된 필드만 사용한다.

## 호출 예시 자리

아래는 호출 주소를 지어내지 않기 위한 작성 틀이다. 실제 경로 및 파라미터는 원본 제공처 문서와 승인 조건을 확인한 뒤 채운다.

```text
GET [원본 안내문에서 확인한 요청 주소]
  ?serviceKey=[서버 환경변수]
  &[원본 문서의 필수 파라미터]

응답 필드: [원본 문서에서 확인한 필드명]
요청 시각: [실제 호출 시각]
자료 기준 시각: [응답에 포함된 시간 필드]
```

## 심사 연결

- **기획성**: 위험 예보와 대상자 및 이송 자원을 한 흐름으로 묶되 예보값만으로 실제 대피 결정을 자동화하지 않는다.
- **활용성**: 플랫폼 내 데이터 항목과 기존 원본 API의 중복을 표로 드러내고, 승인 이후 연결 여부를 기록한다.
- **유용성**: 담당자는 위험 시각과 부족 차량을 함께 확인하고, 시민은 도착 여부를 담당자 및 도우미를 통해 확인한다.
- **협력성**: 데이터 제공기관과 실제 사용 및 검증 협의는 아직 완료되지 않았다. 플랫폼 승인과 기관 협력은 사용자 확인 전 실적으로 기재하지 않는다.
- **충실성**: 확인되지 않은 필드, 주기, 호출 예제는 `확인 필요`로 남긴다. 플랫폼 목록의 갱신일을 갱신 주기로 오인하지 않는다.

## 플랫폼에 목록이 없거나 지역 범위가 다른 항목

- 프로젝트 `client/api/opendata.js`는 공공데이터포털의 민방위 대피시설 API를 이미 호출한다. 플랫폼 데이터 목록에서는 같은 이름의 전국 자료를 찾지 못했고, 지자체별 대피시설 자료는 일부 확인했다. 따라서 기존 연계를 플랫폼 카탈로그가 제공한다고 쓰지 않는다.
- 국립공원 대피소와 서울 수해대피소는 동해시 자료가 아니다. 대피 시설의 데이터 구조를 참고할 후보로만 남기며 동해시 운영 자료로 쓰지 않는다.
