# 현장 소식: 서비스 디자인 설계 문서

작성 기준: 2026. 10. 18. 대상 화면: `/console/notes` (서류 읽기 아래 두 번째 탭)

## 1. 왜 만드는가

- 대피 계산은 대상자마다 이송 등급(침상, 휠체어, 부축, 도보)을 알아야 돌아갑니다. 이 등급은 공공데이터에 없고, 종이 서류와 현장 사람들의 말 속에만 있습니다.
- 서류 읽기는 한 시점의 종이를 읽습니다. 그 뒤에 어르신이 넘어지거나 호전되어도 명부는 그대로입니다. 기획서의 문제 가설 B(명부의 거동 상태가 실제와 다르다)를 직접 겨냥하는 입구입니다.
- 현장 소식은 이미 있는 말을 쓰는 입구입니다. 요양보호사, 이장, 가족이 담당자에게 전화나 문자로 전하는 말을 새 서식 없이 받습니다.

## 2. 누구의 경험인가

| 구분 | 누구 | 이 화면에서 하는 일 |
|---|---|---|
| 앞단 사용자 | 동 재난 담당자 | 전해 들은 말을 붙여 넣거나 녹음을 올리고, AI 제안과 근거를 보고 승인 |
| 소식을 주는 사람 | 요양보호사, 이장과 통장, 가족과 보호자 | 평소처럼 말로 전함. 새로 배울 것이 없음 |
| 결과를 받는 사람 | 도우미, 소방 | 바뀐 등급이 반영된 배정표와 인계 목록 |
| 간접 당사자 | 재난취약자 본인 | 이송 방식이 실제 몸 상태에 맞게 정해짐 |

## 3. 서비스 시나리오 (입력에서 결과까지)

1. 망상동 담당자가 요양보호사에게서 "지난주 넘어지신 뒤 휠체어를 타신다"는 전화를 받습니다.
2. 담당자가 현장 소식 탭에서 대상자를 고르고 말을 그대로 붙여 넣습니다. 통화를 녹음했다면 파일을 올립니다.
3. AI가 소식을 읽고 "부축에서 휠체어로 바뀜"이라는 명부 변경 후보를 만들고, 근거 문구를 소식 원문에서 그대로 가져옵니다.
4. 화면은 현재 명부 값과 제안 값을 나란히 보여 줍니다. 근거 문구는 원문 위에 강조됩니다.
5. 담당자가 반영하면 명부가 바뀌고, 부족분 계산과 배정에 바로 쓰입니다. 반영하지 않으면 명부는 그대로입니다.

## 4. 서비스 블루프린트

| 단계 | 담당자 행동(앞단) | 접점 | 보이지 않는 처리(뒷단) | 지원 요소 |
|---|---|---|---|---|
| 소식 받기 | 말을 붙여 넣거나 음성 파일 올리기 | 소식 받기 카드 | 입력 길이와 파일 크기 확인 | 대상자 선택, 소식 낸 사람 선택 |
| AI가 읽기 | 진행 표시 보며 기다림 | 4단계 진행 표시 | AI가 글을 받아 적고 달라진 점과 근거 문구를 찾음 | Gemini API, 정해진 형식의 결과 |
| 검증 | 아무것도 하지 않음 | 일치도 표시 | 근거 문구가 원문에 있는지 자동 대조, 등급 낮춤 제안 감점 | 규칙 코드(lib/notes.js) |
| 담당자 승인 | 원문과 제안을 견주어 반영, 수정 후 반영, 반영 안 함 | 현장 소식 확인 화면 | 명부 갱신, 입력 방법을 현장 소식으로 기록 | 명부 저장소 |
| 결과 사용 | 부족분 계산과 배정 확인 | 발령 준비 화면 | 바뀐 등급으로 규칙 계산 | 계산 규칙(shortage, assign) |

## 5. 역할 경계: AI와 규칙과 사람

| 하는 곳 | 하는 일 |
|---|---|
| AI | 말이나 음성을 읽고 거동이 달라졌는지 찾기, 근거 문구 붙이기, 특이사항 추가와 해제 후보 내기 |
| 규칙 | 근거 문구 원문 대조, 등급을 낮추는 제안 감점, 등급과 특이사항 모순 감점, 필요 인원과 차량 계산, 배정 |
| 사람(담당자) | 반영 여부 결정. 반영해야만 명부가 바뀜 |

필요 인원과 차량 계산, 3D 상황판은 규칙으로 하는 부분이라 AI라고 설명하지 않습니다.

## 6. 안전 설계

1. **원문 대조:** AI가 낸 근거 문구가 소식 원문에 문자 그대로 있어야 합니다. 없으면 일치도를 확인 필요로 내리고 AI 요약을 화면에서 숨깁니다.
2. **비대칭 주의:** 도움이 덜 필요해지는 변경(예: 휠체어에서 도보)은 일치도를 한 단계 내리고 경고를 붙입니다. 잘못 낮추면 이송에서 빠질 수 있기 때문입니다.
3. **개인정보:** 이름, 주소, 전화번호는 읽거나 출력하지 않습니다. 대상자는 코드로만 고릅니다.
4. **사람의 승인:** 자동 반영이 없습니다. 근거가 없는 제안은 반영하지 않음 한 번으로 닫힙니다.

## 7. 사용성 평가 과제 (인터뷰 때 담당자에게 시킬 일)

설명하지 않고 과제만 줍니다. 말하는 동안 끼어들지 않고, 망설인 곳과 되묻는 곳을 적습니다.

1. "요양보호사가 어르신이 넘어져 휠체어를 타신다고 전화했습니다. 이 화면으로 명부에 반영해 보십시오."
2. "AI가 낸 제안 가운데 반영하면 안 되는 것을 찾아보십시오."(근거가 소식에 없는 사례)
3. "등급이 가벼워지는 제안이 왔습니다. 반영하시겠습니까, 그 이유는 무엇입니까."

관찰 지표: 과제 완료 여부, 걸린 시간, 근거 문구를 보았는지, 위험 표시를 알아챘는지, 담당자가 쓰는 다른 용어.

## 8. 지금의 한계

- 샘플 5종과 처음 화면의 확인 대기 3건은 미리 써 둔 모의 응답입니다. 화면에 "시연용 모의 응답"으로 표시합니다.
- 서버 키(`GEMINI_API_KEY`)가 연결되지 않아 직접 입력한 글과 음성은 아직 AI로 읽히지 않습니다(배포본 `/api/intake`도 같은 상태, 503 확인).
- 음성은 녹음 파일 올리기만 됩니다. 화면에서 바로 녹음하는 기능은 없습니다.
- 정확도는 측정하지 않았습니다. 정답을 사람이 매긴 가짜 소식 묶음으로 일치율을 재는 일이 남아 있습니다.
- 대상자 코드로 고르는 방식이라, 실제 운영에서 소식과 대상자를 연결하는 방법은 동 담당자 인터뷰로 확인해야 합니다.
