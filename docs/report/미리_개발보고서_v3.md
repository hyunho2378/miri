## 1. 개요 (overview) ※ 서비스 정의, 개발 범위, 준비 정도

**산불 재난취약자 이송 준비의 디지털 전환**

### 1-1. 서비스 정의

○ 미리는 대피 기한 안에 옮길 차와 사람의 부족분을 평시에 계산하고 발령 때 배정까지 잇는 지자체 담당자용 웹 서비스임

• 혼자 대피하기 어려운 주민의 이송 부족분을 마을 단위로 평시에 계산하고, 발령 때 차량, 도우미, 대상자를 묶은 배정표를 도우미 휴대폰으로 전달함.

• 사회복지 담당자의 명부 확인, 재난 담당자의 부족분 확인과 발령, 도우미의 이송 보고, 소방의 인계 목록을 하나의 계산 결과로 연결함.

• 계산과 배정은 규칙 코드로 처리하고, AI는 종이 서류와 현장 소식에서 근거 문구를 뽑는 데만 사용함.

| 구분 | 내용 | 근거 |
| --- | --- | --- |
| 시범 지역 | 강원특별자치도 동해시(법정동 37곳, 임시주거시설 27곳) | client/src/mock/donghaeData.js |
| 사용자 | 읍면동 사회복지 담당자, 재난 담당자, 도우미, 소방 | docs/IA.md |
| 디자인 기준 | KRDS(디지털 정부 디자인 시스템) 색과 Pretendard GOV, 무보더 그림자 3단 | client/src/tokens.js |
| 배포 | Vercel 정적 화면과 서버 함수(실행 지역 서울 icn1), 네이버 클라우드 Object Storage 국내 정적 사본 | client/vercel.json |

### 1-2. 개발 범위

○ 1단계는 담당자 화면, 도우미 화면, 서버 함수, 공개 데이터 연계까지 구현 범위로 둠

| 영역 | 1단계 구현 범위 | 2단계 추진 범위 |
| --- | --- | --- |
| 담당자 화면 | 현황판, 서류 읽기, 현장 소식, 대상자 명부, 상황판(3D, 2D), 차량과 도우미, 부족분 계산, 발령 운영, 소방 인계, 이송 기록, 문서함, 설정 | 지자체 계정과 역할별 권한, 행정망 연계 |
| 도우미 화면 | 배정 수락과 불가, 대상자 순서, 출발, 도착, 탑승, 인계, 실패 보고 | 문자 발송, 기기 간 실시간 전달 |
| 서버 | 서류 읽기, 현장 소식, 공공데이터 중계, 법령 확인, 한글 문서 생성, 문서함 저장, 개방 API, 시연 세션 | 실제 명부 저장, 실제 발령 |
| 데이터 | 동해시 공개 자료(인구, 장기요양, 대피소, 집결지, 건물, 지형), 실시간 공공데이터 8종, 시연용 명부 2,013건 | 동의 기반 시범 명부 |

## 2. 서비스 구성 (service) ※ 사용자별 제공 가치, 서비스 원칙, 이용 흐름

**사회복지, 재난, 도우미, 소방을 잇는 하나의 계산 결과**

### 2-1. 사용자별 제공 가치

○ 사용자마다 같은 숫자를 자기 업무 단위로 받아 평시 준비부터 발령 종료까지 이어 감

| --- | --- | --- | --- |
| 사회복지 담당자 | 평시 명부 확인, 서류와 현장 소식 확인 | 서류 사진의 이송 등급 초안과 근거 문구, 명부 변경 후보 | 완료 |
| 재난 담당자 | 평시 부족분 확인, 발령 때 배정 | 마을별 부족분, 필요 추가 차량, 배정표, 재배정, 소방 인계 목록, 공문 | 완료(훈련 발령) |
| 도우미 | 휴대폰 화면 | 내 배정, 대상자 순서, 단추 하나 보고 | 완료(시연 화면) |

| 다른 기관 | 개방 API | 마을별 부족분, 대피소 수용 | 완료 |

### 2-3. 서비스 원칙과 화면 반영

○ 규칙 계산, 담당자 확정, 근거 대조, 개인정보 최소화를 화면 규칙으로 구현함

| 원칙 | 화면 반영 방식 |
| --- | --- |
| 규칙 기반 계산 | 부족분과 배정은 shortageCalc.js, assign.js 규칙 계산 |
| 담당자 확정 | 판독 결과는 확인 대기 목록에 쌓이고 확인, 수정, 제외 뒤 명부와 계산에 반영 |
| 근거 원문 대조 | 서류 원문에 없는 근거 문구는 "원문 불일치" 표시 뒤 목록 맨 위 배치 |
| 개인정보 최소화 | 화면은 대상자 코드만 표시, AI에는 이름, 연락처, 주소를 가린 글자만 전송 |
| 출처와 기준일 | 공공데이터 카드마다 기관, 기관 입력 시각, 포털 수정일 표기 |
| 계산 조건 공개 | 부족분 화면에 계산 규칙 판, 입력 기준, 가정값 점검 카드 |
| 실패 사유 표시 | 공공데이터나 AI 호출 실패 때 빈 값 대신 사유 표기 |

### 2-4. 단계별 이용 흐름

○ 평시 명부 확인에서 종료와 소방 인계까지 7단계로 업무가 이어짐

 ① 명부 확인 → 사회복지 담당자 승인 → 부족분 계산 → 차량 협약과 도우미 지정.

 ② 발령 → 추천 배정 계산 → 담당자 확정 → 도우미 휴대폰 전달.

 ③ 이송 보고 → 재배정 → 기한 초과 대상자 소방 일괄 인계 → 이송 기록 저장.

## 4. 화면별 설명 (screens) ※ 목적, 구성, 동작, 데이터

### 4-1. 현황판 /console

○ 현황판은 오늘 발령 때 옮기지 못할 인원을 아침에 확인하는 첫 화면임

• 미이송 예상 291명과 추천 배정 적용 267명을 맨 위에 두고, 마을별 미이송 막대와 확인할 일 15건을 이어 배치함.

• 명부 2,013건(확인 2,005명, 판독 확인 대기 7건, 중복 의심 1건)과 기준 시나리오(옥계 방면 북측 확산)를 함께 표시함.

• 산림청 산불위험지수, 기상청 특보와 바람, 동해 응급실 가용병상, 장애인편의시설 실시간 연계.

## 5. 디자인 시스템 (design system) ※ 색, 글꼴, 레이아웃, 접근성

**KRDS 원본 토큰 기반의 2색 체계**

### 5-1. 기준과 방향

○ 정부 서비스 표준(KRDS) 원본 토큰을 그대로 쓰고 빨강은 부족과 위험에만 씀

• KRDS(디지털 정부 디자인 시스템) 원본 토큰(github.com/KRDS-uiux/krds-uiux) 적용.

• 유채색은 파랑(KRDS primary)과 빨강(KRDS point) 두 가지로 제한.

• 면 구분은 선 대신 그림자 3단으로 처리.

### 5-2. 색 토큰

| 역할 | 값 | 쓰임 |

| primary hover, text | #0B50D0 | 눌림, 파랑 글자 |
| danger | #D63D4A | 부족 인원, 위험 |
| text pri, sec, meta | #1E2124, #464C53, #58616A | 본문, 보조, 설명 |
| page, canvas | #FFFFFF, #F4F5F6 | 바탕 |
| 문서함 종류색 | 문서 #256EF4, 시트 #0F9D58, 설문 #7A3CFF | 아이콘과 서식 카드 머리 |

### 9-3. 부족분 계산

○ 부족분은 차량 수와 왕복 가능 횟수로 구한 이송 가능 인원을 대상자 수에서 뺀 값임

```
이송 가능 인원 = 차량 수 x 왕복 가능 횟수
왕복 가능 횟수 = (이송 기한 - 준비 시간) / 왕복 시간
왕복 시간     = 집결지에서 임시주거시설까지 도로 주행 시간 x 2 + 탑승과 하차 시간(기본 20분)
부족분        = 대상자 수 - 이송 가능 인원
```
